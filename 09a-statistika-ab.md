## 9А.1. Распределения, которые встречаются в работе

Не нужно знать двадцать распределений. Нужно узнавать пять и понимать, откуда они берутся.

| Распределение | Что описывает | Пример | Параметры |
|---------------|---------------|--------|-----------|
| **Бернулли** | Одно событие «да / нет» | Купил или нет | Вероятность `p` |
| **Биномиальное** | Число успехов в `n` попытках | Сколько из 1000 посетителей купили | `n`, `p` |
| **Пуассона** | Число событий за период | Заказов в час, обращений в день | Среднее `λ` |
| **Нормальное** | Сумма многих мелких независимых влияний | Рост, ошибки измерений, **средние по выборкам** | Среднее, стандартное отклонение |
| **Логнормальное** | Произведение многих влияний; всегда больше нуля, длинный хвост | Чеки, доходы, время на сайте | Параметры логарифма |
| **Экспоненциальное** | Время до следующего события | Время между заказами | Интенсивность |

```python
n_visitors, p = 1000, 0.05

purchases = rng.binomial(n=n_visitors, p=p, size=10_000)       # 10 000 «дней» по 1000 посетителей
print(purchases.mean(), purchases.std())                       # около 50 и около 6.9
print(np.sqrt(n_visitors * p * (1 - p)))                       # теория: корень из n·p·(1−p)

# Вероятности через scipy
print(stats.binom.pmf(50, n_visitors, p))                      # ровно 50 покупок
print(stats.binom.cdf(40, n_visitors, p))                      # 40 или меньше
print(1 - stats.binom.cdf(65, n_visitors, p))                  # больше 65 — аномально много?
```

Последняя строка — рабочий инструмент: «сегодня 66 покупок вместо обычных 50, это событие или шум?» Вероятность получить больше 65 при обычной конверсии — около 1,5 %. Редко, но за два месяца наблюдений такой день случится сам по себе.

У каждого распределения в SciPy один и тот же набор методов:

| Метод | Что возвращает |
|-------|----------------|
| `rvs(size=n)` | Случайные значения |
| `pmf(x)` / `pdf(x)` | Вероятность (плотность) значения |
| `cdf(x)` | Вероятность получить `x` или меньше |
| `sf(x)` | Вероятность получить больше `x`: то же, что `1 − cdf` |
| `ppf(q)` | Значение, ниже которого лежит доля `q` (квантиль) |

```python
print(stats.norm.ppf(0.975))            # 1.96 — то самое число из доверительных интервалов
print(stats.norm.cdf(1.96))             # 0.975
print(stats.poisson.sf(8, mu=4))        # вероятность больше 8 событий при среднем 4
```

## 9А.2. Центральная предельная теорема на практике

ЦПТ утверждает: среднее большой выборки распределено почти нормально, каким бы ни было исходное распределение. Но слово «большой» зависит от того, насколько тяжёлый хвост.

```python
def sample_means(generator, n, repeats=5000):
    return np.array([generator(n).mean() for _ in range(repeats)])

lognormal = lambda n: rng.lognormal(7.5, 0.9, n)

for n in (10, 100, 1000, 10_000):
    means = sample_means(lognormal, n, repeats=2000)
    print(n, "асимметрия средних:", round(stats.skew(means), 2))
```

Асимметрия распределения средних падает с ростом выборки: при десяти наблюдениях она велика, при десяти тысячах почти ноль. Вывод: для скошенных метрик t-тест начинает работать корректно только на больших выборках. При сотне наблюдений в группе ему верить нельзя — нужен бутстрап или перестановочный тест.

### Стандартная ошибка

Стандартная ошибка среднего — стандартное отклонение, делённое на корень из размера выборки:

```python
sample = rng.lognormal(7.5, 0.9, 2000)

se_formula = sample.std(ddof=1) / np.sqrt(len(sample))
se_simulated = sample_means(lognormal, 2000, repeats=2000).std()
print(round(se_formula, 1), round(se_simulated, 1))          # близкие числа
```

Из формулы следует закон, который нужно помнить всегда: **точность растёт как корень из объёма данных**. В 4 раза больше данных — в 2 раза точнее. В 100 раз больше — всего в 10 раз точнее.

## 9А.3. Размер эффекта

P-value отвечает на вопрос «есть ли эффект», но не «насколько он велик». В отчёте всегда должны быть **величина эффекта и интервал для неё**.

```python
control = rng.normal(100, 20, 5000)
treatment = rng.normal(102, 20, 5000)

diff = treatment.mean() - control.mean()                     # абсолютный эффект
lift = treatment.mean() / control.mean() - 1                 # относительный эффект
pooled_std = np.sqrt((control.var(ddof=1) + treatment.var(ddof=1)) / 2)
cohens_d = diff / pooled_std                                 # эффект в стандартных отклонениях

print(f"разница {diff:.2f}, прирост {lift:.2%}, d Коэна {cohens_d:.3f}")
print("p-value:", stats.ttest_ind(treatment, control, equal_var=False).pvalue)
```

| Мера | Что показывает | Когда использовать |
|------|----------------|--------------------|
| Абсолютная разница | На сколько единиц изменилась метрика | Расчёт денег: «+2 рубля с пользователя» |
| Относительный прирост (lift) | На сколько процентов | Сравнение тестов между собой, общение с бизнесом |
| d Коэна | Эффект в стандартных отклонениях | Оценка «заметности» эффекта |

Эффект в 0,1 стандартного отклонения на выборке в 5000 даёт крошечное p-value. Значимость говорит о количестве данных не меньше, чем о величине эффекта.

### Процентные пункты и проценты

Конверсия выросла с 5 % до 6 %. Это **+1 процентный пункт** (абсолютно) и **+20 %** (относительно). Всегда уточняй, о чём речь: фраза «конверсия выросла на 1 %» может означать и то и другое, и разница между трактовками — в двадцать раз.

### Интервал для относительного прироста

```python
def bootstrap_lift_ci(control, treatment, repeats=5000, alpha=0.05):
    lifts = np.empty(repeats)
    for i in range(repeats):
        c = rng.choice(control, len(control), replace=True)
        t = rng.choice(treatment, len(treatment), replace=True)
        lifts[i] = t.mean() / c.mean() - 1
    return np.percentile(lifts, [100 * alpha / 2, 100 * (1 - alpha / 2)])

low, high = bootstrap_lift_ci(control, treatment, repeats=2000)
print(f"прирост {lift:.2%}, 95 % ДИ от {low:.2%} до {high:.2%}")
```

Интервал для отношения нельзя получить, просто поделив границы интервала разницы на среднее контроля: знаменатель тоже случаен. Бутстрап учитывает это автоматически.

## 9А.4. Как выбрать тест

```
Что сравниваем?
│
├─ Доли (конверсия, доля оттока)
│     └─ z-тест пропорций или хи-квадрат
│
├─ Средние
│     ├─ выборки большие, хвост умеренный ......... t-тест Уэлча
│     ├─ хвост тяжёлый или выборки малы ........... бутстрап / перестановочный тест
│     └─ одни и те же объекты «до» и «после» ...... парный t-тест
│
├─ Отношения (CTR, средний чек по заказам) ........ дельта-метод, бутстрап по пользователям
│
├─ Медианы и перцентили ........................... бутстрап
│
└─ Три и больше групп ............................. ANOVA + попарные сравнения с поправкой
```

### Манна — Уитни проверяет не то, что кажется

Этот тест часто советуют «для ненормальных данных вместо t-теста». Но он проверяет другую гипотезу: не равенство средних, а то, что значение из одной группы с вероятностью 50 % больше значения из другой.

```python
# Две группы с ОДИНАКОВЫМ средним, но разной формой распределения
a = rng.exponential(scale=100, size=5000)             # среднее 100, скошено
b = rng.normal(loc=100, scale=10, size=5000)          # среднее 100, симметрично

print(round(a.mean(), 1), round(b.mean(), 1))
print("t-тест:      ", round(stats.ttest_ind(a, b, equal_var=False).pvalue, 3))
print("Манна—Уитни: ", stats.mannwhitneyu(a, b).pvalue)
```

Средние равны, t-тест различий не видит — и он прав. Манна — Уитни уверенно «находит различие», потому что распределения разной формы. Если бизнес интересует **средняя выручка на пользователя** (а она превращается в деньги), этот тест отвечает не на тот вопрос. Обратная ситуация тоже возможна: тест может не заметить роста среднего, если тот получен за счёт нескольких крупных покупок.

Правило: выбирай тест под метрику, по которой принимается решение. Для среднего — тесты про среднее.

### Перестановочный тест

Самый понятный тест из существующих — его можно объяснить без единой формулы.

Идея: если между группами нет разницы, то метки «A» и «B» ничего не значат. Перемешаем их случайно много раз и посмотрим, как часто случайная разница оказывается не меньше наблюдаемой. Эта доля и есть p-value.

```python
def permutation_test(a, b, repeats=5000):
    observed = b.mean() - a.mean()
    combined = np.concatenate([a, b])
    count = 0
    for _ in range(repeats):
        rng.shuffle(combined)
        diff = combined[len(a):].mean() - combined[:len(a)].mean()
        if abs(diff) >= abs(observed):
            count += 1
    return observed, count / repeats

group_a = rng.lognormal(7.5, 0.9, 300)
group_b = rng.lognormal(7.6, 0.9, 300)

observed, p_value = permutation_test(group_a, group_b, repeats=3000)
print(round(observed, 1), p_value)
```

Тест не требует нормальности и работает для любой статистики — среднего, медианы, перцентиля: достаточно заменить `.mean()` на нужную функцию.

## 9А.5. Метрики-отношения и единица анализа

Самая частая **серьёзная** ошибка в анализе A/B-тестов — и её почти не объясняют в учебниках.

Возьмём CTR: клики, делённые на показы. Пользователей делят на группы случайно, поэтому независимы между собой **пользователи**. А показы одного пользователя зависимы: кто-то кликает на всё, кто-то ни на что. Если применить z-тест пропорций к показам, как будто каждый показ независим, разброс окажется сильно занижен, и тест будет находить «эффекты» там, где их нет.

Проверим симуляцией. Сделаем A/A-тест, в котором разницы нет по построению:

```python
def simulate_users(n_users):
    """У каждого пользователя своя склонность кликать и своё число показов."""
    views = rng.poisson(lam=rng.gamma(2.0, 10.0, n_users)) + 1
    click_rate = rng.beta(2, 30, n_users)                    # индивидуальный CTR
    clicks = rng.binomial(views, click_rate)
    return views, clicks


def naive_p_value(views_a, clicks_a, views_b, clicks_b):
    """НЕПРАВИЛЬНО: z-тест, как будто каждый показ независим."""
    p_a, p_b = clicks_a.sum() / views_a.sum(), clicks_b.sum() / views_b.sum()
    pooled = (clicks_a.sum() + clicks_b.sum()) / (views_a.sum() + views_b.sum())
    se = np.sqrt(pooled * (1 - pooled) * (1 / views_a.sum() + 1 / views_b.sum()))
    return 2 * stats.norm.sf(abs((p_b - p_a) / se))


false_alarms = 0
for _ in range(500):
    va, ca = simulate_users(2000)
    vb, cb = simulate_users(2000)
    false_alarms += naive_p_value(va, ca, vb, cb) < 0.05

print("Доля ложных срабатываний наивного теста:", false_alarms / 500)
```

Вместо положенных 5 % наивный тест ошибается в несколько раз чаще. Каждый такой «успех» — фича, выкаченная на всех без пользы.

### Дельта-метод

Правильная дисперсия отношения двух сумм учитывает разброс и числителя, и знаменателя, и связь между ними:

```python
def ratio_and_variance(numerator, denominator):
    """Отношение сумм и дисперсия его оценки (дельта-метод). Данные — по пользователям."""
    n = len(numerator)
    mean_num, mean_den = numerator.mean(), denominator.mean()
    ratio = mean_num / mean_den
    cov = np.cov(numerator, denominator, ddof=1)
    variance = (cov[0, 0] - 2 * ratio * cov[0, 1] + ratio ** 2 * cov[1, 1]) / (mean_den ** 2 * n)
    return ratio, variance


def delta_p_value(views_a, clicks_a, views_b, clicks_b):
    ratio_a, var_a = ratio_and_variance(clicks_a, views_a)
    ratio_b, var_b = ratio_and_variance(clicks_b, views_b)
    z = (ratio_b - ratio_a) / np.sqrt(var_a + var_b)
    return 2 * stats.norm.sf(abs(z))


false_alarms = 0
for _ in range(500):
    va, ca = simulate_users(2000)
    vb, cb = simulate_users(2000)
    false_alarms += delta_p_value(va, ca, vb, cb) < 0.05

print("Доля ложных срабатываний дельта-метода:", false_alarms / 500)       # около 0.05
```

Альтернатива без формул — **бутстрап по пользователям**: в каждом повторе выбираем с возвращением пользователей целиком, вместе со всеми их показами и кликами, и пересчитываем отношение.

### Правило

**Единица анализа должна совпадать с единицей рандомизации.** Делили пользователей — анализируй пользователей. Какие метрики это затрагивает:

| Метрика | Числитель | Знаменатель | Нужен дельта-метод? |
|---------|-----------|-------------|---------------------|
| Конверсия пользователя в покупку | Купившие пользователи | Все пользователи | Нет: одна строка на пользователя |
| Выручка на пользователя (ARPU) | Выручка | Пользователи | Нет |
| CTR | Клики | Показы | **Да** |
| Средний чек | Выручка | Заказы | **Да** |
| Конверсия сессии в заказ | Заказы | Сессии | **Да** |
| Доля успешных поисков | Успешные поиски | Все поиски | **Да** |

Простой способ избежать проблемы — пересчитать метрику на пользователя: вместо «CTR по показам» взять «средний CTR пользователя» или «клики на пользователя». Но это уже другая метрика с другим смыслом, и выбирать её надо до теста.

## 9А.6. Мощность: симуляция вместо формул

Формула размера выборки из главы 9 работает для простых случаев. Для любой нестандартной метрики мощность проще **посчитать симуляцией**: много раз сгенерировать тест с известным эффектом и посмотреть, как часто он его находит.

```python
def simulated_power(n, lift, repeats=1000, alpha=0.05):
    """Мощность t-теста для логнормальной метрики при заданном относительном эффекте."""
    detected = 0
    for _ in range(repeats):
        a = rng.lognormal(7.5, 0.9, n)
        b = rng.lognormal(7.5, 0.9, n) * (1 + lift)
        detected += stats.ttest_ind(a, b, equal_var=False).pvalue < alpha
    return detected / repeats

for n in (1000, 5000, 20_000):
    print(n, simulated_power(n, lift=0.05, repeats=400))
```

Эффект в 5 % на метрике с тяжёлым хвостом при тысяче пользователей в группе находится реже чем в каждом пятом тесте, при пяти тысячах — примерно в половине. Привычные 80 % мощности достигаются только около десяти тысяч пользователей в группе. Запускать такой тест на маленькой выборке бессмысленно: почти наверняка он «ничего не покажет», а команда сделает ложный вывод, что идея не работает.

Преимущество симуляции: вместо `rng.lognormal` можно подставить **настоящие исторические данные** — выбирать пользователей из прошлого периода, искусственно добавлять эффект одной группе и считать тест. Так получают мощность именно для своей метрики, со всеми её особенностями.

### MDE при фиксированной выборке

Часто вопрос стоит наоборот: трафик ограничен, тест может идти две недели — какой эффект мы вообще способны заметить?

```python
def mde_for_proportion(p, n, alpha=0.05, power=0.8):
    """Минимальный обнаруживаемый абсолютный эффект для конверсии при n пользователях в группе."""
    z_alpha = stats.norm.ppf(1 - alpha / 2)
    z_beta = stats.norm.ppf(power)
    return (z_alpha + z_beta) * np.sqrt(2 * p * (1 - p) / n)

for n in (5000, 20_000, 80_000):
    mde = mde_for_proportion(0.05, n)
    print(f"n = {n:>6}: MDE = {mde:.4f} ({mde / 0.05:.1%} относительно)")
```

При пяти тысячах пользователей в группе MDE — 24 % относительно. Если реалистичный эффект от изменения — 2–3 %, такой тест запускать не стоит: он заведомо ничего не докажет. Лучше узнать это до запуска.

## 9А.7. Множественные сравнения

Проверяем двадцать метрик при α = 0,05. Даже если изменение не влияет ни на что, в среднем одна метрика окажется «значимой» случайно.

```python
def any_false_positive(n_metrics, repeats=2000, alpha=0.05):
    """Вероятность получить хотя бы одну «значимую» метрику, когда эффекта нет ни в одной."""
    p_values = rng.uniform(0, 1, size=(repeats, n_metrics))      # при верной H0 p-value равномерно
    return (p_values.min(axis=1) < alpha).mean()

for k in (1, 5, 20):
    print(k, round(any_false_positive(k), 3), "теория:", round(1 - 0.95 ** k, 3))
```

При двадцати метриках шанс хотя бы одной ложной находки — 64 %.

```python
def bonferroni(p_values, alpha=0.05):
    """Самая строгая: порог делится на число сравнений."""
    return np.asarray(p_values) < alpha / len(p_values)


def holm(p_values, alpha=0.05):
    """Чуть мягче Бонферрони и никогда не хуже неё."""
    p_values = np.asarray(p_values)
    order = np.argsort(p_values)
    significant = np.zeros(len(p_values), dtype=bool)
    for position, index in enumerate(order):
        if p_values[index] < alpha / (len(p_values) - position):
            significant[index] = True
        else:
            break                              # как только одна не прошла — остальные тоже
    return significant


def benjamini_hochberg(p_values, alpha=0.05):
    """Контролирует долю ложных находок среди всех находок (FDR)."""
    p_values = np.asarray(p_values)
    n = len(p_values)
    order = np.argsort(p_values)
    thresholds = alpha * np.arange(1, n + 1) / n
    passed = p_values[order] <= thresholds
    significant = np.zeros(n, dtype=bool)
    if passed.any():
        significant[order[: np.where(passed)[0].max() + 1]] = True
    return significant


p_values = [0.001, 0.008, 0.012, 0.04, 0.2, 0.6]
print("без поправки:      ", (np.array(p_values) < 0.05).sum())
print("Бонферрони:        ", bonferroni(p_values).sum())
print("Холм:              ", holm(p_values).sum())
print("Бенджамини—Хохберг:", benjamini_hochberg(p_values).sum())
```

| Поправка | Что контролирует | Когда использовать |
|----------|------------------|--------------------|
| Бонферрони | Вероятность хотя бы одной ложной находки | Сравнений мало, цена ошибки высока |
| Холм | То же, но с большей мощностью | Всегда вместо Бонферрони |
| Бенджамини — Хохберг | Долю ложных среди найденных | Сравнений много: десятки сегментов, метрик |

### Как с этим жить

Поправки снижают мощность, поэтому лучшая стратегия — уменьшить число сравнений:

- **одна** целевая метрика, выбранная до теста: по ней решение, к ней поправка не нужна;
- несколько **контрольных** метрик — они должны «не ухудшиться», а не «улучшиться»;
- всё остальное — **исследовательские** наблюдения: источник гипотез для следующих тестов, но не основание для решения.

То же относится к сегментам. «В целом эффекта нет, но у новых пользователей на Android — есть» — это гипотеза для отдельного теста, а не результат.

Несколько вариантов в одном тесте (A/B/C/D) — тоже множественные сравнения: три пары «вариант против контроля» требуют поправки.

## 9А.8. Снижение дисперсии: CUPED

Чем меньше разброс метрики, тем меньший эффект можно заметить на той же выборке. Метод CUPED уменьшает разброс, используя данные о пользователях **до начала теста**.

Идея: поведение пользователя в тесте во многом предсказывается его поведением раньше — кто много покупал в прошлом месяце, много купит и в этом. Эта «предсказуемая» часть не связана с тестом, и её можно вычесть.

```python
n = 5000
pre_a = rng.lognormal(7.0, 0.8, n)                          # траты до теста
pre_b = rng.lognormal(7.0, 0.8, n)
during_a = 0.7 * pre_a + rng.lognormal(6.0, 0.8, n)         # траты в тесте связаны с прошлыми
during_b = (0.7 * pre_b + rng.lognormal(6.0, 0.8, n)) * 1.03    # в группе B эффект +3 %

# Коэффициент theta считается один раз по обеим группам вместе
metric_all = np.concatenate([during_a, during_b])
covariate_all = np.concatenate([pre_a, pre_b])
theta = np.cov(metric_all, covariate_all, ddof=1)[0, 1] / covariate_all.var(ddof=1)

# Из метрики вычитается её «предсказуемая» часть
adj_a = during_a - theta * (pre_a - covariate_all.mean())
adj_b = during_b - theta * (pre_b - covariate_all.mean())

print("p-value без CUPED:", round(stats.ttest_ind(during_a, during_b, equal_var=False).pvalue, 4))
print("p-value с CUPED:  ", round(stats.ttest_ind(adj_a, adj_b, equal_var=False).pvalue, 4))
print("снижение дисперсии:", round(1 - adj_a.var() / during_a.var(), 2))
print("корреляция с ковариатой:", round(np.corrcoef(during_a, pre_a)[0, 1], 2))
```

Что важно понимать:

- Среднее метрики CUPED **не меняет** — эффект остаётся тем же. Уменьшается только шум.
- Снижение дисперсии равно квадрату корреляции между метрикой и ковариатой. Корреляция 0,7 убирает около половины дисперсии — это равносильно удвоению выборки.
- Ковариата должна быть измерена **до теста**. Если взять что-то, на что тест мог повлиять, результат будет искажён.
- У новых пользователей истории нет, для них CUPED бесполезен.
- Лучшая ковариата — та же метрика за период до теста.

Родственные приёмы: **стратификация** (сравнивать внутри однородных слоёв — платформ, стран — и взвешивать результат) и ограничение выбросов сверху (перцентиль 99) — оно тоже резко снижает дисперсию денежных метрик, но слегка меняет саму метрику.

## 9А.9. Подглядывание и последовательное тестирование

В главе 9 мы видели: если смотреть на p-value каждый день и останавливаться при первом значении ниже 0,05, ложных срабатываний становится 25 % вместо 5 %. На практике смотреть всё равно хочется — и иногда нужно: если новая версия ломает оплату, ждать две недели нельзя.

Варианты решения:

**1. Фиксированный горизонт.** Размер выборки определён заранее, решение принимается один раз. Смотреть на графики можно, принимать решение об успехе — нет. Досрочная остановка разрешена только при явной поломке.

**2. Более строгий порог на промежуточных проверках.** Если запланировано `k` проверок, для каждой используют порог жёстче 0,05. Простейший вариант — делить α на число проверок; на практике применяют специальные границы (О'Брайена — Флеминга), которые почти не тратят α на ранние проверки.

```python
def peeking_false_positive_rate(n_total, n_looks, threshold, repeats=1000):
    false_positives = 0
    checkpoints = np.linspace(n_total / n_looks, n_total, n_looks).astype(int)
    for _ in range(repeats):
        a = rng.normal(0, 1, n_total)
        b = rng.normal(0, 1, n_total)
        for n in checkpoints:
            if stats.ttest_ind(a[:n], b[:n]).pvalue < threshold:
                false_positives += 1
                break
    return false_positives / repeats

print("5 проверок, порог 0.05: ", peeking_false_positive_rate(2000, 5, 0.05, repeats=600))
print("5 проверок, порог 0.01: ", peeking_false_positive_rate(2000, 5, 0.01, repeats=600))
```

С порогом 0,05 при пяти проверках ложных срабатываний около 13 %, с порогом 0,01 — около 3 %: в пределах допустимого, ценой некоторой потери мощности.

**3. Специальные последовательные методы** (mSPRT, «всегда-валидные» p-value) позволяют смотреть когда угодно. Они встроены в крупные платформы экспериментов; достаточно знать, что они существуют.

## 9А.10. Что ещё ломает эксперименты

### Несоответствие размеров групп (SRM)

Проверка из главы 9, которую нужно делать **первой**, до любых метрик. Типичные причины SRM:

- редирект в одной из групп работает медленнее, и часть пользователей уходит до записи события;
- боты попадают в одну группу чаще;
- баг в новой версии мешает логированию;
- фильтр при анализе («только те, кто дошёл до экрана X») зависит от самой фичи.

Последний пункт коварнее всего. Если анализировать только тех, кто **увидел** новую кнопку, группы перестают быть сравнимыми: условие отбора зависит от воздействия. Сравнивать нужно всех, кто был **назначен** в группу.

### Эффекты новизны и привыкания

```
Эффект
  │ ██
  │ ████
  │ ██████▄▄
  │ ██████████▄▄▄▄▄▄▄▄▄▄▄▄   ← настоящий долгосрочный эффект
  └──────────────────────── дни
```

Новое привлекает внимание само по себе; через неделю-две эффект спадает. Бывает и наоборот: пользователи сначала теряются в новом интерфейсе, а потом привыкают. Проверка: построй эффект по дням теста и отдельно — только для **новых** пользователей, у которых нет старых привычек.

### Сетевые эффекты

A/B-тест предполагает, что пользователи одной группы не влияют на другую. Это неверно в маркетплейсах (тестовая группа скупает товар, контрольной не достаётся), соцсетях, такси и доставке (общий пул водителей и курьеров). Там делят не пользователей, а города, районы или промежутки времени.

### Сезонность и длительность

- Тест должен идти целое число недель: состав аудитории в будни и выходные разный.
- Не запускай тесты в аномальные периоды: праздники, распродажи, сбои.
- Слишком короткий тест захватывает в основном самых активных пользователей: они приходят чаще и попадают в тест в первые дни. Их реакция может отличаться от реакции остальных.

### Разбавление

Если фичу видят только 10 % пользователей группы, а анализируются все 100 %, эффект разбавляется в десять раз и тонет в шуме. Решение — анализировать тех, кто **мог** увидеть изменение: условие отбора должно быть одинаковым для обеих групп и не зависеть от самой фичи. Например, «открыл страницу корзины» — если изменение находится на странице корзины и не влияет на то, откроют ли её.

### Заражение между тестами

В компании одновременно идут десятки тестов. Обычно они независимы, но тесты, меняющие одно и то же место, могут конфликтовать. Проверка — посмотреть результат отдельно в срезах другого теста.

## 9А.11. Когда A/B-тест невозможен

Иногда разделить пользователей нельзя: изменение цен для всех, рекламная кампания на телевидении, новый закон, запуск в целом городе. Тогда используют методы причинно-следственного анализа. Они слабее эксперимента, но лучше наивного «до и после».

### Почему «до и после» не работает

Запустили фичу 1 марта, в марте выручка выросла на 10 %. Заслуга фичи? Неизвестно: 8 Марта, сезон, рекламная кампания, общий рост рынка. Сравнение «до и после» приписывает изменению всё, что случилось одновременно с ним.

### Разность разностей (difference-in-differences)

Нужна контрольная группа, которую изменение не затронуло, — например, другой город. Идея: сравниваем не уровни, а **изменения**.

```python
data = {
    #                 до     после
    "Казань (тест)":    (100.0, 125.0),
    "Самара (контроль)": (90.0, 104.0),
}

change_test = data["Казань (тест)"][1] - data["Казань (тест)"][0]              # +25
change_control = data["Самара (контроль)"][1] - data["Самара (контроль)"][0]   # +14

print("Наивное «до и после»:", change_test)
print("Разность разностей:  ", change_test - change_control)                  # +11
```

Из 25 единиц роста в Казани 14 случились бы и так — столько же выросла Самара без всякой фичи. Эффект — 11.

Ключевое допущение — **параллельные тренды**: без воздействия обе группы менялись бы одинаково. Проверяют его по периоду до запуска: если линии на графике шли параллельно, допущению можно верить.

### Другие подходы — знать по названиям

| Метод | Идея |
|-------|------|
| **Синтетический контроль** | Контрольная группа собирается как взвешенная смесь нескольких регионов, повторяющая поведение тестового до запуска |
| **Разрывный дизайн** | Сравниваются объекты чуть выше и чуть ниже порога: скидку дали тем, у кого чек от 5000, — сравниваем 4990 и 5010 |
| **Сопоставление (matching)** | Каждому «получившему воздействие» подбирается похожий «не получивший» |
| **Причинный анализ временного ряда** | По истории строится прогноз «что было бы без изменения» и сравнивается с фактом |

Общий принцип: всё это способы построить **контрфактическую** оценку — что произошло бы без воздействия. A/B-тест делает это лучше всех, потому что случайное разделение гарантирует сравнимость групп.

## 9А.12. Байесовский подход: чуть глубже

В главе 9 мы получили вероятность того, что B лучше A. Байесовский анализ даёт ещё одну полезную для решений величину — **ожидаемые потери**.

```python
visitors_a, orders_a = 10_000, 500
visitors_b, orders_b = 10_000, 540

post_a = rng.beta(1 + orders_a, 1 + visitors_a - orders_a, 200_000)
post_b = rng.beta(1 + orders_b, 1 + visitors_b - orders_b, 200_000)

prob_b_better = (post_b > post_a).mean()
loss_if_choose_b = np.maximum(post_a - post_b, 0).mean()      # сколько теряем, если B на самом деле хуже
loss_if_choose_a = np.maximum(post_b - post_a, 0).mean()

print(f"P(B лучше A) = {prob_b_better:.3f}")
print(f"Ожидаемые потери при выборе B: {loss_if_choose_b:.5f}")
print(f"Ожидаемые потери при выборе A: {loss_if_choose_a:.5f}")
```

Вероятность, что B лучше, — около 90 %. По частотным меркам «не значимо». Но ожидаемые потери при выборе B в двадцать с лишним раз меньше, чем при выборе A: если B и хуже, то совсем чуть-чуть, а если лучше — заметно. Когда внедрение ничего не стоит, выбор очевиден.

### Априорное распределение

`Beta(1, 1)` — «ничего не знаем заранее». Но обычно мы знаем: конверсия нашего сайта — около 5 %, а не 50 %. Это знание можно заложить:

```python
weak_prior = (1, 1)                 # ничего не знаем
informed_prior = (50, 950)          # «как будто уже видели 1000 посетителей с конверсией 5 %»

for name, (alpha, beta) in [("слабый", weak_prior), ("информативный", informed_prior)]:
    posterior = stats.beta(alpha + 3, beta + 17)             # наблюдали 3 покупки из 20
    low, high = posterior.ppf([0.025, 0.975])
    print(f"{name:<14} среднее {posterior.mean():.3f}, 95 % интервал {low:.3f}–{high:.3f}")
```

На двадцати посетителях слабый априор даёт оценку около 18 % с огромным интервалом. Информативный удерживает её возле 5 %: три покупки из двадцати — слишком мало данных, чтобы поверить в конверсию 15 %. Чем больше данных, тем меньше влияние априорного распределения.

Байесовский подход не отменяет главных правил: подглядывание и множественные сравнения вредят и ему, просто менее заметно.

## 9А.13. Отчёт по тесту

Результат теста — это документ, по которому принимают решение. Структура:

```
1. Решение (одна строка)
   Рекомендуем внедрять / не внедрять / продлить тест.

2. Что тестировали
   Гипотеза: если ..., то ..., потому что ...
   Группы, доли трафика, даты, платформы.

3. Корректность
   Размеры групп и проверка SRM.
   Длительность: целое число недель? Достигнут ли расчётный размер выборки?
   Не было ли сбоев и аномальных дней.

4. Целевая метрика
   Значения в группах, абсолютная и относительная разница,
   95 % доверительный интервал, p-value.

5. Контрольные метрики
   Что не должно было ухудшиться — и ухудшилось ли.

6. Дополнительные наблюдения
   Динамика эффекта по дням, сегменты — с пометкой «исследовательское».

7. Оценка эффекта в деньгах
   Сколько это даст в месяц или год, с диапазоном по границам интервала.

8. Ограничения и следующие шаги
```

Пример хорошей формулировки результата:

> Конверсия в заказ выросла с 4,82 % до 5,11 % (+0,29 п. п., +6,0 %). 95 % ДИ: от +0,05 до +0,53 п. п., p = 0,018. Средний чек не изменился (−0,4 %, ДИ от −2,1 % до +1,3 %). Ожидаемый эффект на выручку — от 0,9 до 9,5 млн рублей в год. Рекомендуем внедрять.

Чего не должно быть в отчёте:

- «значимо» без величины эффекта и интервала;
- сегмент, найденный после теста, в роли главного результата;
- «тест не показал значимых различий, значит, эффекта нет» — правильно: «эффект, если он есть, меньше MDE»;
- красивого графика, оборванного в день, когда результат выглядел лучше всего.

### Чек-лист перед запуском

- [ ] Гипотеза записана в формате «если — то — потому что».
- [ ] Выбрана одна целевая метрика и несколько контрольных.
- [ ] Посчитаны размер выборки и длительность; MDE реалистичен.
- [ ] Определена единица рандомизации; метрики-отношения считаются корректно.
- [ ] Проверено, что A/A-тест на этой системе даёт 5 % ложных срабатываний.
- [ ] Заранее записано, какое решение будет принято при каждом исходе.

### Чек-лист при анализе

- [ ] Нет SRM.
- [ ] Тест шёл запланированное время.
- [ ] Использован тест, выбранный до запуска.
- [ ] Посмотрены выбросы: не определил ли результат один пользователь.
- [ ] Эффект по дням не затухает.
- [ ] Контрольные метрики не ухудшились.
- [ ] В выводе есть размер эффекта, интервал и оценка в деньгах.

### Задание 1. Распределения

```python
lam = 12

print("P(20 и больше):", round(stats.poisson.sf(19, mu=lam), 4))        # около 0.021

threshold = stats.poisson.ppf(1 - 0.001, mu=lam)
print("Порог аномалии:", threshold)                                      # 24
print("P(больше порога):", round(stats.poisson.sf(threshold, mu=lam), 5))
```

Число событий за период описывается распределением Пуассона. `sf(19)` — вероятность получить **больше 19**, то есть 20 и больше; с `sf(20)` получилась бы вероятность 21 и больше. Ошибка на единицу в таких расчётах — самая частая.

Двадцать заказов при среднем двенадцати случаются примерно раз в 50 часов — это не аномалия. Аномальным стоит считать час с 25 заказами и больше.

Оговорка: реальный поток заказов обычно разбросан сильнее пуассоновского, потому что интенсивность зависит от времени суток и дня недели. Порог нужно считать отдельно для каждого часа дня или брать из исторических перцентилей.

### Задание 2. ЦПТ для экспоненциального распределения

```python
def skew_of_means(n, repeats=20_000):
    means = rng.exponential(scale=1.0, size=(repeats, n)).mean(axis=1)
    return stats.skew(means)

for n in (10, 50, 100, 400, 1000):
    print(n, round(skew_of_means(n), 3))
```

Асимметрия средних падает как `2 / √n`: при `n = 100` она около 0,2, при `n = 400` — около 0,1. Значит, нужно больше четырёхсот наблюдений.

Массив генерируется сразу двумерным — `repeats` строк по `n` значений, — и среднее берётся по строкам. Это в десятки раз быстрее цикла; приём векторизации из главы 4.

### Задание 3. Перестановочный тест для медианы

```python
def permutation_test_stat(a, b, statistic=np.median, repeats=3000):
    observed = statistic(b) - statistic(a)
    combined = np.concatenate([a, b])
    extreme = 0
    for _ in range(repeats):
        rng.shuffle(combined)
        diff = statistic(combined[len(a):]) - statistic(combined[:len(a)])
        extreme += abs(diff) >= abs(observed)
    return observed, extreme / repeats

a = rng.lognormal(7.5, 0.9, 1000)
b = rng.lognormal(7.7, 0.9, 1000)

observed, p_perm = permutation_test_stat(a, b)
print("разница медиан:", round(observed, 1), "p-value:", p_perm)
print("Манна—Уитни:   ", round(stats.mannwhitneyu(a, b).pvalue, 4))
```

Функция принимает статистику параметром — тот же код проверит разницу средних, 90-х перцентилей или чего угодно. Это паттерн «стратегия» из главы 2В.

Оба теста дадут маленькое p-value: здесь распределения одной формы и отличаются сдвигом, а в такой ситуации Манна — Уитни и сравнение медиан согласуются. Расходятся они, когда меняется форма распределения — как в примере раздела 9А.4.

### Задание 4. Средний чек

```python
def simulate_orders(n_users):
    """Возвращает по пользователям: число заказов и суммарную выручку."""
    orders = rng.poisson(lam=rng.gamma(2.0, 1.5, n_users)) + 1
    user_level = rng.lognormal(7.0, 0.6, n_users)                 # у каждого свой типичный чек
    revenue = np.array([rng.lognormal(np.log(level), 0.4, k).sum() for level, k in zip(user_level, orders)])
    return orders, revenue


def delta_p_value(num_a, den_a, num_b, den_b):
    def ratio_var(num, den):
        ratio = num.mean() / den.mean()
        cov = np.cov(num, den, ddof=1)
        return ratio, (cov[0, 0] - 2 * ratio * cov[0, 1] + ratio ** 2 * cov[1, 1]) / (den.mean() ** 2 * len(num))
    ratio_a, var_a = ratio_var(num_a, den_a)
    ratio_b, var_b = ratio_var(num_b, den_b)
    return 2 * stats.norm.sf(abs(ratio_b - ratio_a) / np.sqrt(var_a + var_b))


def naive_p_value(orders_a, revenue_a, orders_b, revenue_b):
    """НЕПРАВИЛЬНО: t-тест по заказам, как будто они независимы."""
    checks_a = np.repeat(revenue_a / orders_a, orders_a)          # каждому заказу — средний чек его пользователя
    checks_b = np.repeat(revenue_b / orders_b, orders_b)
    return stats.ttest_ind(checks_a, checks_b, equal_var=False).pvalue


naive, delta = 0, 0
REPEATS = 300
for _ in range(REPEATS):
    oa, ra = simulate_orders(1500)
    ob, rb = simulate_orders(1500)
    naive += naive_p_value(oa, ra, ob, rb) < 0.05
    delta += delta_p_value(ra, oa, rb, ob) < 0.05

print("Наивный тест по заказам:", naive / REPEATS)
print("Дельта-метод:           ", delta / REPEATS)
```

Наивный тест ошибается заметно чаще 5 %, дельта-метод держится около 5 %. Причина та же, что и с CTR: заказы одного пользователя похожи друг на друга, поэтому независимых наблюдений меньше, чем строк в таблице заказов.

Чем сильнее различаются пользователи между собой и чем больше у них заказов, тем сильнее ошибается наивный тест.

### Задание 5. Мощность симуляцией

```python
def power_proportion_simulated(p, lift, n, repeats=2000, alpha=0.05):
    successes_a = rng.binomial(n, p, repeats)
    successes_b = rng.binomial(n, p * (1 + lift), repeats)
    p_a, p_b = successes_a / n, successes_b / n
    pooled = (successes_a + successes_b) / (2 * n)
    z = (p_b - p_a) / np.sqrt(pooled * (1 - pooled) * 2 / n)
    return (2 * stats.norm.sf(np.abs(z)) < alpha).mean()


def power_proportion_formula(p, lift, n, alpha=0.05):
    p2 = p * (1 + lift)
    se = np.sqrt((p * (1 - p) + p2 * (1 - p2)) / n)
    return stats.norm.cdf(abs(p2 - p) / se - stats.norm.ppf(1 - alpha / 2))


for n in (5000, 10_000, 20_000, 40_000):
    print(n, round(power_proportion_simulated(0.05, 0.10, n), 3), round(power_proportion_formula(0.05, 0.10, n), 3))
```

Симуляция и формула совпадают с точностью до случайной погрешности. Мощность 80 % достигается примерно при 31 тысяче пользователей в группе — то же число, что давала функция `sample_size` из главы 9.

Здесь не понадобился цикл: `rng.binomial` сразу генерирует результаты двух тысяч тестов, и все p-value считаются векторно.

### Задание 6. Множественные сравнения

```python
def simulate_p_values(n_tests=1000, n_metrics=10, n=2000, effect=0.1):
    """Первая метрика с эффектом, остальные — без. Возвращает матрицу p-value."""
    p_values = np.empty((n_tests, n_metrics))
    for metric in range(n_metrics):
        shift = effect if metric == 0 else 0.0
        a = rng.normal(0, 1, size=(n_tests, n))
        b = rng.normal(shift, 1, size=(n_tests, n))
        p_values[:, metric] = stats.ttest_ind(a, b, axis=1).pvalue
    return p_values


def bh_mask(p_row, alpha=0.05):
    order = np.argsort(p_row)
    passed = p_row[order] <= alpha * np.arange(1, len(p_row) + 1) / len(p_row)
    mask = np.zeros(len(p_row), dtype=bool)
    if passed.any():
        mask[order[: np.where(passed)[0].max() + 1]] = True
    return mask


p = simulate_p_values()
methods = {
    "без поправки": p < 0.05,
    "Бонферрони": p < 0.05 / p.shape[1],
    "Бенджамини—Хохберг": np.array([bh_mask(row) for row in p]),
}

for name, significant in methods.items():
    false_found = significant[:, 1:].any(axis=1).mean()        # хотя бы одна ложная находка
    true_found = significant[:, 0].mean()                      # настоящий эффект найден
    print(f"{name:<20} ложная находка: {false_found:.3f}   настоящий эффект найден: {true_found:.3f}")
```

Типичная картина: без поправки ложная находка есть примерно в 37 % тестов. Бонферрони снижает её до 5 %, но и настоящий эффект находит заметно реже — примерно в 65 % тестов вместо 88 %. Бенджамини — Хохберг здесь почти не отличается от Бонферрони: настоящий эффект всего один из десяти. Его преимущество в мощности проявляется, когда настоящих эффектов несколько.

Вывод тот же, что в разделе 9А.7: поправки стоят мощности, поэтому лучше заранее сократить число проверяемых метрик.

### Задание 7. CUPED и корреляция

```python
def variance_reduction(correlation, n=20_000):
    covariate = rng.normal(0, 1, n)
    noise = rng.normal(0, 1, n)
    metric = correlation * covariate + np.sqrt(1 - correlation ** 2) * noise    # заданная корреляция
    theta = np.cov(metric, covariate, ddof=1)[0, 1] / covariate.var(ddof=1)
    adjusted = metric - theta * (covariate - covariate.mean())
    return np.corrcoef(metric, covariate)[0, 1], 1 - adjusted.var() / metric.var()

for target in (0.3, 0.6, 0.9):
    actual, reduction = variance_reduction(target)
    print(f"корреляция {actual:.2f}: дисперсия снижена на {reduction:.1%} (теория: {target ** 2:.1%})")
```

Снижение дисперсии равно квадрату корреляции: 9 %, 36 % и 81 %. При корреляции 0,3 метод почти бесполезен, при 0,9 — равносилен пятикратному увеличению выборки.

Практический вывод: прежде чем внедрять CUPED для метрики, посчитай её корреляцию со значением за предыдущий период. Для стабильных метрик (число сессий, траты постоянных клиентов) она высока, для редких событий (покупка раз в полгода) — близка к нулю.

### Задание 8. Разность разностей

```python
weeks = np.arange(1, 13)
launch_week = 9                                   # запуск в тестовом городе с 9-й недели

control = 200 + 5 * weeks + rng.normal(0, 4, 12)
test = 260 + 5 * weeks + rng.normal(0, 4, 12)
test[weeks >= launch_week] += 30                  # настоящий эффект: +30

before = weeks < launch_week

# 1. Проверка параллельных трендов по периоду до запуска
slope_test = stats.linregress(weeks[before], test[before]).slope
slope_control = stats.linregress(weeks[before], control[before]).slope
print(f"Наклон до запуска: тест {slope_test:.2f}, контроль {slope_control:.2f}")

gap_before = test[before] - control[before]
print("Разрыв между городами до запуска:", gap_before.round(1))

# 2. Оценка эффекта
change_test = test[~before].mean() - test[before].mean()
change_control = control[~before].mean() - control[before].mean()

print(f"Наивное «до и после»: {change_test:.1f}")
print(f"Разность разностей:   {change_test - change_control:.1f}")
```

Наклоны до запуска близки, разрыв между городами держится около 60 без тренда — допущение параллельных трендов правдоподобно.

Наивное сравнение даёт около 60: оно приписывает фиче и общий рост, который шёл в обоих городах. Разность разностей возвращает оценку, близкую к настоящему эффекту 30.

Если бы до запуска разрыв между городами систематически рос или сокращался, метод применять было бы нельзя: он приписал бы фиче продолжение уже существовавшего расхождения.
